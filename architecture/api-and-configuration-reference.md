The management QR response contains `tableId`, `number`, `label`, `path`, `url`, and `concurrencyToken`. The path is `/t/{slug}/q/{code}` and the URL uses `Public:AppBaseUrl`. Regeneration takes the current token and replaces the code at commit. The guest resolver returns `cafeName`, `branchId`, `branchName`, `tableId`, and `tableNumber`. Missing and malformed code paths use the same rate limit and `404 GuestQr.NotFound` contract. QR responses use `Cache-Control: no-store`. Allowed origins can read `Retry-After` on a `429` response.

The guest order submission body carries `code` (the table QR code), `serviceType` (`DineIn` or `Takeaway`), `guestDisplayName`, an optional `expectedTotal`, and `lines` of `productId`, `sizeId`, `addonIds`, `quantity`, `expectedUnitPrice`, and `expectedAddonPrices`. The table is resolved from the QR code only; a body table identifier is never accepted. Success returns `201` with `orderNumber`, `publicReference`, `status`, `totalAmount`, and `responseDeadline`, and sets `Location` to `/t/{slug}/api/v1/guest/orders/{publicReference}`, which is the guest status route. The `Idempotency-Key` header is required: the idempotency identity covers the QR-resolved table, the service type, the source, the guest display name, and the ordered lines (product, size, quantity, and add-on ids). Repeating the same key with the same values returns the same order; changing any of those values under the same key returns `409 Idempotency.KeyReused`. The expected prices, the expected total, and the device header are not part of that identity: the server recomputes every price, and the device value is untrusted metadata. Price or availability changes return `409 Orders.PriceChanged` (with `items` and `currentTotal` extensions) or `409 Orders.ProductUnavailable` (with an `items` extension); validation failures return `400`; every rejected QR context returns the same `404 GuestQr.NotFound`. The optional `X-Guest-Device` header is accepted only when it is 16 to 64 characters from `A-Z a-z 0-9 - _`; any other value is ignored rather than rejected, and the stored value is never trusted for security decisions. Responses use `Cache-Control: no-store`.

The guest status route `GET t/{slug}/api/v1/guest/orders/{publicReference}` is anonymous and answerable before any staff decision: it expires the order when its response window has elapsed, so the guest always sees `Pending`, `Accepted`, `Rejected`, or `Expired` instead of an open pending order. The reference is validated as 22 base64url characters before any database access, and an unknown or malformed reference returns the same `404 GuestQr.NotFound` as every other guest context, so a reference is never confirmed or denied. The response carries `orderNumber`, `status`, `rejectionReason` only when the status is `Rejected`, `tableNumber`, `serviceType`, `items` (`productName`, `sizeName`, `quantity`, `addonNames`), `totalAmount`, `submittedAt`, and `responseDeadline`; staff names, staff ids, the guest device id, station names, and audit data are never returned. Guests may poll the route; the recommended interval is 3 to 5 seconds and the global rate limit is the abuse protection. The reference is never logged. Responses use `Cache-Control: no-store`.

The staff order feed is a polling endpoint: `GET t/{slug}/api/v1/orders` pages one branch's orders newest first with the id as tie-breaker, filtered by `status` (`Pending`, `Accepted`, `Rejected`, `Expired`) and by `updatedSince`, which returns only orders whose last change is strictly newer than the given timestamp (inclusive-exclusive rule: pass the last seen change time to reconcile after a reconnect). The response carries order id, number, table number, service type, status, guest display name, submitted time, response deadline, items (name, size, add-on names, quantity, station name), the total, and the last change time (`updatedAt`), which a client passes back as `updatedSince` to reconcile; the guest device id is never returned. Staff assigned to stations see only the items of their active stations plus unrouted items, with the order number and status staying visible, and orders that end up with no visible items are dropped; staff without station assignments see every station of their branch. Staff are fixed to their branch; the owner must pass `branchId`, and a different branch returns the same uniform 404. `GET t/{slug}/api/v1/orders/{orderId}` returns one order under the same scope rules, and a foreign order is indistinguishable from a missing one.

Order decisions require `orders.decide`: `POST t/{slug}/api/v1/orders/{orderId}/accept` takes no body, and `POST t/{slug}/api/v1/orders/{orderId}/reject` takes a body with `reason`, trimmed text of 3 to 256 characters with no control characters that the guest can see, so a reason must never include personal data. Only pending orders can be decided: a non-pending order returns `409 Orders.StatusConflict` with a `currentStatus` extension, and a lost concurrency race returns `409 Orders.StatusConflict` with the current status. Pending orders are expired lazily at the start of the feed read and of every decision (expiry first), so a decision on an order whose response window has elapsed returns `409 Orders.StatusConflict` naming `Expired`. Station-scoped staff may decide an order only when at least one of its items belongs to their stations or is unrouted, staff without station assignments may decide any order of their branch, the owner may decide orders of any branch, and a foreign order returns the same uniform 404. Each decision is audited with the old and new status and, for a rejection, the reason; the guest name and device id are never audited. The decision response carries the order id, order number, the new status, and the response time.

Captains holding `orders.captain` place an assisted order with `POST t/{slug}/api/v1/orders/assisted` and the required `Idempotency-Key`: the body carries `tableId`, `serviceType`, `guestDisplayName`, an optional `expectedTotal`, and the same `lines` as a guest order. The table must be Active and belong to the caller's branch, the owner may use any branch, and a foreign or inactive table is indistinguishable from a missing order (uniform 404). The order reuses the guest validation, pricing, numbering, and idempotency identity with source Captain, so price or availability changes and a reused key with different values return the same conflicts as a guest order. It is stored with the captain as creator and responder, without a guest device id, and is `Accepted` immediately, so it never expires and creates no miss. Each assisted order is audited as `orders.assisted_created.succeeded` with the order number as the only field; the guest name is never audited. The response is `201` with the order number, public reference, status `Accepted`, and total.

The guest mute register is staff-facing and never blocks by network address. `POST t/{slug}/api/v1/guest-mutes` takes `orderId`, a `reason` of 3 to 256 trimmed characters with no control characters, and an optional `expiryHours` (default 24, maximum 168); the device comes from the stored order, so staff never type the identifier, and the order is resolved only inside the caller's branch (the owner may use any branch, and a foreign order is the uniform 404). Repeating a mute while one is active returns that record unchanged and does not extend it, and an order without a device id returns `400 Guests.DeviceRequired`. Muting never rejects or deletes an order: the order stays stored and is hidden from the default feed only, and `includeMuted=true` brings it back so staff can still decide it. The feed also reports `suggestMute` when a device collected three rejected orders in the last 24 hours; the flag is a hint and nothing is muted automatically. The device id is never audited and the register masks it to its first and last four characters. `POST t/{slug}/api/v1/guest-mutes/{muteId:guid}/lift` stores the lifting staff member and time, and an already lifted or expired mute returns 200 unchanged. `GET t/{slug}/api/v1/guest-mutes` pages the register newest first with `active` and `mutedByUserId` filters; `GET t/{slug}/api/v1/guest-mutes/summary` returns, per acting staff member, the number of mutes created in a UTC date range and how many were lifted early, ordered by count descending then name. Both reads require `guests.mute.audit`, staff are fixed to their branch, and the owner passes `branchId`.

The per-table bill is staff-facing and keeps payment separate from order preparation. `GET t/{slug}/api/v1/bills` pages one branch's bills newest first with the id tie-breaker, filtered by `tableId` and `status` (`Open` or `Closed`); every row carries the bill's accepted-order total, its confirmed-payment total, and the remaining amount, and both totals are derived at read time and never stored. `GET t/{slug}/api/v1/bills/{billId:guid}` returns the bill with its orders grouped by guest display name — orders without a name group under `Guest` — with each person's total, paid, and remaining: a person's paid amount counts only the confirmed payments linked to that person's orders, so a bill-level payment reduces the bill but no person. `settlementType` is `Cash`, `Online`, or `Hybrid`, derived from the methods present, and is null until money is recorded. Staff are fixed to their branch and the owner passes `branchId` for the list; a foreign bill returns the same uniform 404 as a missing one. Once an order is attached to its table bill, the guest status response also carries `billReference`, the bill's public reference, without changing any existing field.

Cash is recorded only by an authorized confirmation: `POST t/{slug}/api/v1/bills/{billId:guid}/payments/cash` requires `payments.cash.confirm` and the `Idempotency-Key` header, takes `amount` and an optional `orderId`, and stores the amount, the confirming staff member, and the server time as a `Confirmed` payment — choosing Cash in a client proves nothing on its own. An amount above the remaining amount of the bill, or of the linked order when `orderId` is present, returns `409 Billing.AmountAboveRemaining`; a linked order of another bill returns `409 Billing.OrderNotOnBill`; a closed bill returns `409 Billing.BillClosed`; and repeating the same key returns the same payment without counting twice. A payment never writes the order status, and an order decision never marks money as paid: paid and remaining are computed from `Confirmed` payments only. The bill closes automatically in the same transaction as the payment that brings the remaining amount to zero and never while a payment is pending review; `POST t/{slug}/api/v1/bills/{billId:guid}/close` lets a holder of `bills.close` close it with a mandatory `reason` of 3 to 256 trimmed characters while money is still owed, closing an already closed bill returns it unchanged, and a new order after closing opens a new bill. Closing is refused with `409 Billing.PendingProof` while a proof awaits review. Each confirmation is audited as `payments.cash.confirmed.succeeded` with the method, status, amount, bill, and order only, and each close as `bills.closed.succeeded` with the reason and the remaining amount; the idempotency key, the guest name, and the device id are never audited.

The cafe online payment option is staff-configured: `GET` and `PUT t/{slug}/api/v1/payment-settings` require `payments.settings.manage` and carry `onlineEnabled`, `methodLabel` (default `InstaPay`, up to 32 characters), `paymentLink`, `paymentAddress`, `displayName`, and a `concurrencyToken`. The link must be an absolute https URL of up to 512 characters, the address up to 128 characters without control characters, and enabling requires at least one of them; a stale token returns `409 PaymentSettings.ConcurrencyConflict`. Updates are audited with the old and new values because the link and address are business data, not secrets. `GET t/{slug}/api/v1/guest/qr/{code}/payment-options` is anonymous, rate limited, returns the enabled flag, label, link, address, and display name for the QR's cafe, and returns the uniform `404 GuestQr.NotFound` for an unusable code without audit data.

A guest submits one payment screenshot against a bill: `POST t/{slug}/api/v1/guest/bills/{billReference}/payment-proofs` is anonymous, rate limited, guest-allow-listed, and takes multipart `image` (JPEG, PNG, or WebP), `claimedAmount`, and an optional `note` of up to 140 characters plus the required `Idempotency-Key`. The image is stored through the media storage under the payment proof purpose, and a `PendingReview` Online payment keeps the media reference, the claimed amount, and the note. The claimed amount must be positive and not above the bill's remaining amount (`409 Billing.AmountAboveRemaining`), at most three proofs may await review per bill (`409 Billing.PendingProofLimitReached`), an unknown or closed bill is the uniform `404 GuestQr.NotFound`, and repeating the key returns the same proof without a second upload. Success returns `201` with the payment id, status, and claimed amount only; the note, the media key, and the image are never returned or audited.

Guest refund requests are submitted against a confirmed payment. `GET t/{slug}/api/v1/guest/bills/{billReference}/payments` lists the bill's confirmed payments as `paymentId`, `method`, `amount`, and `confirmedAt`; `POST t/{slug}/api/v1/guest/bills/{billReference}/refund-requests` accepts multipart `paymentId`, `claimedAmount`, `reason`, optional `details`, optional `guestDisplayName`, up to five `evidence` files, and a required `Idempotency-Key`. Both routes are anonymous, globally rate limited, and guest-allow-listed. The payment must belong to the referenced bill; the claim must be positive and no greater than its amount less already approved refunds. A bill may have at most three open or in-review requests (Proposed, pending owner confirmation). Evidence is stored with the tenant-scoped refund evidence purpose. Repeating the same key for the same bill returns the existing request without uploading evidence again; reusing it on another bill returns `409 Idempotency.KeyReused`. Success returns `201` with only `publicReference` and `status`, and `Location` points to the status route. `GET t/{slug}/api/v1/guest/refund-requests/{publicReference}` returns `status` and reveals `resolutionNote` only after approval or rejection; malformed and unknown bill or request references return the uniform `404 GuestQr.NotFound`. Staff identity, evidence keys, and evidence contents are never returned or audited.

Staff handle refund requests with `refunds.view` for reads and `refunds.manage` for changes, always inside branch scope: staff are pinned to their branch, the owner reaches every branch, and a foreign request is the same uniform `404 RefundRequests.NotFound` as a missing one. `GET t/{slug}/api/v1/refund-requests` pages newest first with the id tie-breaker, filtered by `status`, `branchId`, `assignedUserId`, and `billId`; a staff member who passes another branch gets the uniform 404, and the owner may omit `branchId` to read every branch (Proposed, pending owner confirmation; the alternative was to require a branch for everyone). `GET t/{slug}/api/v1/refund-requests/{refundRequestId:guid}` returns the request with its append-only events and its attachment metadata; media keys and file contents are never returned. `GET t/{slug}/api/v1/refund-requests/{refundRequestId:guid}/attachments/{attachmentId:guid}` streams the validated evidence with its detected content type, `X-Content-Type-Options: nosniff`, and `Cache-Control: no-store`, so evidence is never publicly cacheable. `POST t/{slug}/api/v1/refund-requests/{refundRequestId:guid}/assign` takes `assignedUserId` and accepts only an active staff member of the request's branch or the owner; anything else returns `400 RefundRequests.AssignedStaffNotFound`. `POST t/{slug}/api/v1/refund-requests/{refundRequestId:guid}/status` takes `status` (`InReview`, `Approved`, or `Rejected`) and an optional `note` that is mandatory for a decision; a decided request cannot change again and a lost concurrency race both return `409 RefundRequests.StatusConflict`, while `409 RefundRequests.ConcurrencyConflict` reports a concurrent change. Every status change appends an event and writes an audit entry with only the old and new status; the reason, details, notes beyond the event note, and evidence are never audited. Approval records only the cafe's agreement: no payment, bill, order, or receipt is changed and no payment provider is called.

Staff review online payments with `payments.online.review` and their branch scope. `GET t/{slug}/api/v1/payments` pages one branch's payments newest first with the id tie-breaker, filtered by `status` and `billId`; staff are fixed to their branch and the owner passes `branchId`, and a foreign branch is the uniform 404. `GET t/{slug}/api/v1/payments/{paymentId:guid}/proof` returns the stored image with its detected content type, `X-Content-Type-Options: nosniff`, and `Cache-Control: no-store`, so a proof is never publicly cacheable; a cash payment, a foreign payment, and a missing file are all the uniform `404 Billing.PaymentNotFound`. `POST t/{slug}/api/v1/payments/{paymentId:guid}/confirm` records an optional `amount` that defaults to the claimed amount and may not exceed the remaining amount (`409 Billing.AmountAboveRemaining`), storing the confirmed amount, the reviewing staff member, and the server time; a lower amount leaves the rest of the bill payable by another proof or cash, and a new remainder is never claimed automatically. `POST t/{slug}/api/v1/payments/{paymentId:guid}/reject` requires a `reason` of 3 to 256 trimmed characters without control characters. Both decisions act only on a `PendingReview` payment, so repeating a decision returns the same result without counting twice or writing a second audit record, and a payment already in the other terminal state returns `409 Billing.PaymentNotPendingReview` naming its status. Confirm and reject are audited as `payments.online.confirmed.succeeded` and `payments.online.rejected.succeeded` with changed fields only: the status, the confirmed amount and time, and the rejection reason; the guest note, the media key, the image, and the idempotency key are never audited. Confirming a payment that brings the remaining amount to zero closes the bill when no proof is pending, and a bill is never treated as fully paid while an Online payment is still `PendingReview`; `Hybrid` is derived when confirmed Cash and Online payments exist on the same bill.

A digital receipt is the immutable record of a fully paid bill and is a convenience record, never tax-compliance proof (FR-REC-002). `GET t/{slug}/api/v1/receipts/{receiptId:guid}` and `GET t/{slug}/api/v1/bills/{billId:guid}/receipt` require `bills.view` and the caller's branch scope: staff are pinned to their branch, the owner may read any branch, and a foreign or missing receipt is the same uniform `404 Receipts.NotFound`. `GET t/{slug}/api/v1/guest/receipts/{billReference}` is anonymous, rate limited, guest-allow-listed, and resolves the bill from its 22-character public reference only; a malformed reference, an unpaid bill, and an unknown bill all return the uniform `404 GuestQr.NotFound`, and the guest response uses `Cache-Control: no-store`. Every receipt response carries `receiptNumber`, `issuedAt`, `totalAmount`, `paidAmount`, `remainingAmount`, the lines grouped by `guestDisplayName` with each group's total, and each payment's `method`, `amount`, and `confirmedAt`; internal ids and staff identity are never returned. The snapshot is created once, when the bill reaches zero remaining with nothing pending, and is never recomputed from the live order, product, or payment state.

The WiFi surface is cafe-level unless noted. `GET` and `PUT t/{slug}/api/v1/wifi/settings` require `wifi.manage` and return or replace the cafe `policy` (`Free` or `Paid`) with its opaque `concurrencyToken`; a stale token returns `409 Wifi.ConcurrencyConflict`, a cafe without a row reads as `Free`, and the response carries the free branch networks visible in the caller's branch scope. `PUT t/{slug}/api/v1/branches/{branchId:guid}/wifi/network` sets that branch's SSID, security (`None`, `WPA`, or `WEP`), and optional guest-visible password; a blank SSID clears the network with `204`, staff may touch only their own branch, and a foreign or missing branch is the uniform `404 Wifi.NotFound`. The password is guest-visible business data and is never logged or stored in an audit snapshot.

Paid WiFi packages live under `t/{slug}/api/v1/wifi/packages` and also require `wifi.manage`: the list is paginated by `page`, `pageSize`, and `includeTotalCount` with an optional `status`, orders by sort order then id, and each package carries `name`, `durationMinutes`, optional `speedMbps`, `dataMode` (`Unlimited` or `Limited` with `quotaMb`), `price`, `sortOrder`, and `status`. Create, update, deactivate, and reactivate are refused with `409 Wifi.PackagesRequirePaidPolicy` while the policy is Free; a duplicate active name is `409 Wifi.PackageNameConflict`, a stale token is `409 Wifi.PackageConcurrencyConflict`, and packages are retired through `Inactive`, never deleted. Updates are audited with the old and new field values, including the price.

Each branch has its own WiFi QR, separate from the table QR: `GET t/{slug}/api/v1/branches/{branchId:guid}/wifi/qr` and `POST .../wifi/qr/regenerate` require `wifi.manage` and return the link path and full URL built from `Public:AppBaseUrl`. The path is `/t/{slug}/w/{code}`, the code is an unguessable 22-character value produced by the same generator as table QRs, the first management read creates the row lazily, and regeneration replaces the code in place so the old code stops resolving. The code is never logged or audited. `GET t/{slug}/api/v1/guest/wifi/{code}` is anonymous, rate limited, guest-allow-listed, and `Cache-Control: no-store`: under the Free policy it returns only the branch network details, under Paid it returns only the Active packages with name, duration, speed, data mode, and price, and a malformed, unknown, regenerated, or unusable code is the uniform `404 GuestQr.NotFound`. The guest response carries no internal ids and no staff identity.

A paid WiFi package can be bought in two ways. In the normal table order both order endpoints accept a line carrying `wifiPackageId` (with empty product, size, and add-on fields) beside product lines; the server prices the package from the active catalog, ignores the client's expected package price, and adds it once to the order and bill total. The package must be Active, the cafe policy must be Paid, and at least one Available voucher must exist for the package, otherwise the submission returns `409 Orders.WifiPackageUnavailable`, `409 Orders.WifiPolicyNotPaid`, or `409 Orders.WifiVoucherUnavailable` and nothing is charged. `POST t/{slug}/api/v1/guest/wifi/{code}/orders` is anonymous, rate limited, guest-allow-listed, requires `Idempotency-Key`, and takes `packageId` plus `guestDisplayName`; it creates a `WifiOnly` order with no table, accepts it automatically, gives it its own new bill, and returns the same `201` shape as the table order with a `Location` to the guest status route. A repeat under the same key returns the same order. The guest status and order feed return a null table number for these orders, and receipts copy the package line like any other line. Voucher assignment and the issued code are added in CFMD-443.

When an order with a package line is accepted, one Available voucher of that package is claimed atomically (`FOR UPDATE SKIP LOCKED`, with the unique order-item index as the final guard); a repeat keeps the same voucher and a race never shares one. An exhausted pool does not fail the order: the order stays accepted and the line appears in the issued lookup as `AwaitingVoucher`. The code is released only after payment: confirmed payments linked to the order cover its total, or the whole bill is fully paid; before that the guest status shows the package line with `wifiCodePending: true` and no code. Once released, the guest order status line carries `wifiCode`, `wifiDurationMinutes`, and `wifiSpeedMbps`, and a receipt issued at payment snapshots the code on its WiFi line. Staff holding `wifi.manage` or `wifi.lookup` use `GET t/{slug}/api/v1/wifi/issued` (paged; filters `packageId`, `status` = `AwaitingVoucher`, `AwaitingPayment`, or `Released`, `orderNumber`, and the order business `date`) to see the package, order number and reference, assignment time, code, and derived status within their branch scope; the owner may pass `branchId`. Voucher issue is audited with the package and order ids and never the code; the code stays out of logs and out of the guest response until release. Redemption by a router or captive portal is not built; the voucher pool remains the Proposed method pending TBD-07 and TBD-08.

The printer registry is per branch under `t/{slug}/api/v1/branches/{branchId:guid}/printers`, with document routes under `/print-routes`, both requiring `printers.manage` and the caller's branch scope (staff are fixed to their branch; the owner passes `branchId`). A printer carries a name, an optional station, an informational connection kind, an Active/Inactive status, and one closed ESC/POS profile: `Escpos80mm` at 48 columns and `Escpos58mm` at 32 columns, both with code page CP437. Adding a profile or changing its width/code page is a code change, not a configuration change; the payload and connector translate the profile into printer commands. `PUT .../print-routes` sets the one primary printer for a branch, optional station (NULL is the branch-wide default), and document type (`OrderTicket` or `Receipt`); a route to an Inactive printer returns `409 Printers.PrinterInactive`, a station from another branch returns `400 Printers.InvalidStation`, and a concurrent route change returns `409 Printers.RouteConflict`. This documents supported pilot profiles and limits only and makes no claim of universal printer compatibility; the owner records the tested printer models separately (TBD-13 is open). The connector applications and printer drivers are separate products and are not built here.

The print queue is visible to staff under `t/{slug}/api/v1/branches/{branchId:guid}/print-jobs`. `GET` requires `printers.manage` and the caller's branch scope, returns the newest job first, and filters by `status` (`Queued`, `Claimed`, `Succeeded`, `Failed`, or `Cancelled`), `printerId`, and `documentType` (`OrderTicket` or `Receipt`); an unknown filter returns `400 Printers.InvalidJobFilter`. Each job carries its ids, document and source type, source id, status, `attempts`, `maxAttempts`, `lastErrorCode`, `leaseExpiresAt`, timestamps, and the structured `documentPayload`. `POST .../print-jobs/{jobId}/cancel` cancels a Queued, Claimed, or Failed job and is refused with `409 Printers.JobNotCancellable` for a printed job; `POST .../print-jobs/{jobId}/requeue` returns only a Failed job to Queued with `attempts` reset to zero and the last error cleared, otherwise `409 Printers.JobNotRequeuable`. Both actions are audited with the old and new status (and, for requeue, the attempts and last error), and a foreign or missing job is the uniform `404 Printers.JobNotFound`.

Connector registrations live under `.../print-connectors` and require `printers.manage`: `GET` lists the branch's connectors with name, status, and last-seen time, `POST` registers one and returns its key exactly once in that response (only the SHA-256 hash is stored, and it is never listed, logged, or audited), and `POST .../print-connectors/{connectorId}/revoke` retires it so its key stops working; a foreign or missing connector is `404 Printers.ConnectorNotFound`, and creation and revocation are audited.

The local connector calls `POST t/{slug}/api/v1/connector/print/claim`, `POST .../connector/print/jobs/{jobId}/succeeded`, and `POST .../connector/print/jobs/{jobId}/failed` with the `X-Connector-Key` header. These routes are anonymous to the user pipeline, but every request is authenticated by the key, compared in constant time after hashing, limited per key (120 requests per 60 seconds), and confined to the key's branch; a missing, malformed, unknown, revoked, or mismatched key is the same `401 Printers.ConnectorUnauthorized`. A claim returns the oldest Queued job of that branch and leases it for 60 seconds (204 when the queue is empty), a claim on an expired lease returns that job to Queued, and a successful claim records the connector's last-seen time. A success report is the only path to `Succeeded`. A failure report takes one of the closed codes `PrinterOffline`, `PaperOut`, `PayloadRejected`, or `Unknown`, increments `attempts`, and returns the job to Queued, or to `Failed` once the third attempt fails; a report on a job that is not claimed returns `409 Printers.JobNotReportable`, and an unknown or foreign job returns `404 Printers.JobNotFound`. The connector lease and the per-key rate limit are code constants, so this story adds no configuration setting. The Windows and Android connector applications and the printer drivers translate the profile and structured payload into ESC/POS commands; they are separate products and are not built here.

The order feed and the decision endpoints expire stale pending orders lazily (no background sweeper in this story): a pending order at or past its `response_deadline` becomes `Expired` in one update, and the first expiry of an order records one missed-response row with the branch and the expiry time plus the holders snapshot of the branch's active staff holding `orders.decide` at that moment. Staff with station assignments are included only when one of their stations matches a routed item or the order has unrouted items, and off-shift staff are included because attendance does not exist yet (Proposed, pending owner confirmation). A repeated expiry records no second miss (the order is unique per miss). The missed-summary endpoint pages one branch's missed counts per staff for a date range over the UTC calendar days of the expiry time, ordered by count descending then name; staff are fixed to their branch, the owner passes `branchId`, and no payroll or deduction logic exists. The response window stays configured by `Orders:ResponseWindowSeconds` (30 to 3600, default 300).

The guest menu is one paged item list (`items`, `page`, `pageSize`, `totalCount`, `hasNextPage`) rather than a category tree, because the pagination contract applies to items; every item carries `categoryId`, `categoryName`, `parentCategoryId`, and `parentCategoryName` so a client can group the page. Items return `id`, `name`, `description`, `kind`, `caffeine`, `preparationMinutes`, `sizes` (`id`, `name`, `price`, `isDefault`), `addons` (`id`, `name`, `price`), and `tags`. Station, status, audit, and availability-reason data are never returned. Sort fields are `sortOrder`, `name`, `createdAt`, and `id`; the default is `sortOrder ASC, id ASC`, an unknown field or unfiltered best-selling request returns `400 Validation.Failed`, and page size is capped by the pagination configuration.

Menu category responses contain `id`, `parentId`, `name`, `sortOrder`, `status`, and `concurrencyToken`. Tree roots also have `children`. Both levels sort by `sortOrder` and then `id`. The tree uses `page`, `pageSize`, and `includeTotalCount` for roots. The default `includeInactive=false` shows active roots and their active children. A granted expansion includes inactive and parent-hidden rows in their original hierarchy. An unauthorized expansion returns `403 Identity.Forbidden`.

Invalid create parents return a generic `400 Validation.Failed` for `parentId`. Category state conflicts return `409 MenuCategories.NameConflict`, `409 MenuCategories.ConcurrencyConflict`, or `409 MenuCategories.ParentInactive`. Missing and inaccessible category IDs return `404 MenuCategories.NotFound`. Update and lifecycle success return 200 with the category. A current-token request that leaves the row unchanged preserves its token and creates no mutation audit record. Repeating a create while its active sibling name is reserved returns a name conflict.

Product list items return `id`, `name`, `kind`, `caffeine`, `categoryId`, `defaultSizePrice`, and `status`; the default size price is null when no active default size exists. Full product responses return sizes, add-ons, stable-ID active tags and `concurrencyToken`. Read-only callers always receive Active products only; inactive and missing products return `404 Products.NotFound`. Size and add-on price changes use `price.size.<id>` and `price.addon.<id>` audit keys. Name conflicts on active sizes or add-ons return `409 Products.NameConflict`; default-size conflicts return `409 Products.DefaultSizeConflict`. Stale tokens return `409 Products.ConcurrencyConflict` subject to the lifecycle visibility rules below.

Inventory items are cafe-wide, so reusable stock definitions carry no branch; received stock lives in per-branch batches. Item responses contain `id`, `name`, `unit`, `lowStockThreshold`, `tracksExpiry`, `nearExpiryDays`, `status`, and `concurrencyToken`, and the list orders by name then id. The unit is one closed set (`Kg`, `G`, `L`, `Ml`, `Piece`, `Pack`); an unknown unit returns `400 Inventory.InvalidUnit`, a duplicate active name returns `409 Inventory.ItemNameConflict`, and a stale token returns `409 Inventory.ConcurrencyConflict`. Missing items return `404 Inventory.ItemNotFound`. Reads require `inventory.view`, item writes require `inventory.manage`, and receiving requires `inventory.receive`. A receipt carries `itemId`, `receivedQuantity`, `receivedDate`, and an optional `expiryDate` as ISO dates; an expiry-tracking item requires an expiry date that is not before the received date, a non-tracking item refuses one, an inactive item returns `409 Inventory.ItemInactive`, and a missing, inactive, or out-of-scope branch returns `404 Inventory.BranchNotFound`. The `Idempotency-Key` header identifies the receipt per branch: repeating it with the same values returns the same batch, and different values under the same key return `409 Idempotency.KeyReused`. Batch list responses carry `id`, `itemId`, `branchId`, `receivedQuantity`, `remainingQuantity`, `receivedDate`, `expiryDate`, and `receivedByUserId`; the `expiryFrom`/`expiryTo` filters keep only batches with an expiry date inside the inclusive range, and batches without an expiry date are excluded by either bound.

Stock alerts are stored per item, branch, and batch: a low-stock alert is raised by the check that runs after a receipt or movement when the summed remaining quantity reaches or falls below the item's `lowStockThreshold`, and near-expiry and expired alerts are raised for batches that still hold stock within the item's `nearExpiryDays` window or past their expiry. Raising an open condition twice keeps one open alert, clearing the condition resolves it, and a resolved alert stays in the history. `GET t/{slug}/api/v1/inventory/alerts` pages alerts newest first, filtered by `kind` (`LowStock`, `NearExpiry`, `Expired`), `state` (`Open`, `Resolved`), and `branchId`, and returns the item name, branch, batch, the quantity for a low-stock alert or the batch remaining quantity and expiry date for an expiry alert, plus the raised, resolved, and notified times; staff are fixed to their active branch. Each newly raised alert is sent once through the notification boundary, and a failed send keeps the alert with no notified time. The provider and channel stay open (TBD-09) and there is no scheduled evaluation: expiry alerts are evaluated on the alert list and stock overview reads. Stock levels and movement history are derived from the stored batches and movements, never from a separate balance. `GET t/{slug}/api/v1/inventory/stock` pages one row per item and branch that has at least one batch, with the summed `remainingQuantity` and the nearest `nearestExpiryDate` among batches that still hold stock; staff are fixed to their active branch and the owner may pass `branchId` and `itemId`. `GET t/{slug}/api/v1/inventory/movements` pages the history newest first with the id as the tie-breaker, filtered by `itemId`, `branchId`, `type`, `createdFrom`, and `createdTo`; the date bounds are inclusive UTC calendar days, and an undefined type or a reversed range returns `400`. `POST t/{slug}/api/v1/branches/{branchId:guid}/inventory/movements` requires `inventory.move` and the `Idempotency-Key` header, takes `itemId`, an optional `batchId`, `type` (`Consume`, `Waste`, or `Adjust`), a signed `quantity`, and a mandatory `reason`, and returns the affected movement rows; Consume and Waste allocate batches by earliest expiry then oldest receipt and refuse a quantity above the available stock, Adjust needs a chosen batch and stays between zero and the received quantity, expired batches can be wasted but not consumed (Proposed, pending owner confirmation), and repeating the key with the same values returns the same movements. Stock totals reconcile with receipts plus adjustments minus consumption and waste for the same data.

The attendance surface is cafe-wide for settings and branch-scoped for everything else. `GET` and `PUT t/{slug}/api/v1/attendance/settings` require `attendance.manage` and read or replace the single mode row (`Off` by default, `Qr`, or `Device`) with its opaque `concurrencyToken`; a stale token returns `409 Attendance.ConcurrencyConflict` and every change is audited with the old and new mode only. `POST t/{slug}/api/v1/attendance/branches/{branchId:guid}/qr` requires `attendance.qr.manage`, works only in `Qr` mode (`409 Attendance.QrModeNotEnabled` otherwise), and returns `branchId`, `token`, `validFrom`, and `validTo`: the token is 32 random bytes as 43 base64url characters, unique, valid for 10 minutes (Proposed, pending owner confirmation), and a still-valid session is returned again instead of a new one. The token appears only in that response and is never logged or audited, and rotation happens server-side by window.

`POST t/{slug}/api/v1/attendance/scan` takes `token` and requires only `TenantUser`: identity and branch come from the signed-in account, never from the token or the body, and one scan is a check-in or the pairing check-out of the open record. An unknown, expired, wrong-branch, off-mode, or replayed token all return the same `400 Attendance.InvalidToken` without creating a record, a deactivated account or one without an active assigned branch is refused with `403 Identity.Forbidden`, and a staff member never has two open records. `GET t/{slug}/api/v1/attendance` requires `attendance.view` and pages one branch's records newest first with the id tie-breaker, filtered by `staffId` and an inclusive `from`/`to` UTC date range over the check-in time, returning the staff name, branch name, check-in and check-out times, both session ids, and the source; a Device row has a null check-in session. Staff are fixed to their branch, the owner passes `branchId`, a foreign branch is the uniform 404, and a reversed range returns `400 Attendance.InvalidDateRange`.

Device attendance registers a fingerprint device per branch and maps its user codes to staff. `POST t/{slug}/api/v1/attendance/devices` returns the key once and stores only its SHA-256 hash; the key is never logged, audited, or returned again. `GET` lists the branch's devices including revoked ones, `POST .../{deviceId}/revoke` marks one revoked, and `PUT .../codes` plus `DELETE .../codes/{staffId}` maintain the one code per staff member and one staff member per code rules (`409 Attendance.DeviceCodeConflict` on a collision). Ingestion requires `Device` mode (`409 Attendance.DeviceModeNotEnabled` otherwise). `POST t/{slug}/api/v1/connector/attendance/events` is anonymous to the user pipeline but authenticated by `X-Connector-Key` with the same per-key fixed window (120 requests per 60 seconds), accepts 1-100 events, and returns one outcome per event (`Processed`, `Duplicate`, `Unmatched`, or `Rejected`) without exposing other staff data. Events are idempotent by device and device event id, carry an optional `In`/`Out` hint that is recorded while pairing follows the QR rule, and are accepted only within 7 days backfill and 5 minutes in the future (Proposed, pending owner confirmation); an out-of-window or out-of-order event is rejected individually without failing the batch. A matched event creates a check-in or closes the open record with the event time, an unknown or unusable code is stored `Unmatched` with no record, and `GET t/{slug}/api/v1/attendance/unmatched` plus `POST t/{slug}/api/v1/attendance/unmatched/reprocess` let an `attendance.manage` holder review the code and retry it after mapping; the reprocess writes one audit entry with the counts. Attendance adds no configuration setting: the ten-minute window, the token size, the 100-event batch, and the 5-minute/7-day device window are code constants.

The dashboard is one read surface for the owner's numbers and never claims net profit (FR-ANL-004). `GET t/{slug}/api/v1/dashboard` requires `reports.view` and returns `metricDefinitions` beside every metric for the inclusive `from` date and exclusive `to` date resolved in the cafe time zone, with an optional `branchId`; `GET t/{slug}/api/v1/dashboard/{metric}` returns the same definition with that one value and `404 Dashboard.UnknownMetric` for a key outside the catalog. Staff are fixed to their assigned branch even when they pass another `branchId`, the owner may pass any branch or omit it to read every branch, and a range longer than 366 days or an end that is not after its start returns `400` from the existing dashboard validators. Sales, collected, orders, average order value, and the cash and online split come from Accepted orders and Confirmed payments only; best sellers, peak hours, the WiFi attach rate, and near-expiry items come from order item snapshots and open stock alerts, and the attach rate is null with a reason under the Free WiFi policy. Guest names, device ids, and staff identity are never returned. The revenue and AOV definitions remain Proposed, pending owner confirmation (TBD-16).

Revenue leakage is a read surface of signals, never a claim of verified loss (FR-ANL-003). `GET t/{slug}/api/v1/dashboard/leakage` requires `reports.view`, takes the same `from`, `to`, and optional `branchId` as the dashboard, and reuses the same cafe time zone and range validators, so staff stay fixed to their branch and the owner reads the requested branch or every branch. The response carries a `notice` stating that each entry is a signal to investigate, not a verified loss, the four definitions, and one entry per signal with its key, count, value, and up to 50 contributors of `id`, `total`, and `occurredAt`; the contributor page follows the request page and reports whether more records exist. The signals are `rejectedAndExpiredOrders` (order totals at submission, selected by decision time), `billsClosedWithAmountOwed` (the remaining amount at closing, the bill's Accepted order total minus its Confirmed payments), `rejectedPaymentProofs` (claimed amounts, selected by rejection time), and `salesCollectedGap` (the net difference between Sales and Collected over closed bills, labelled a gap). `GET t/{slug}/api/v1/dashboard` links to this surface through its `leakage.signalCount` only, the number of signals with at least one record, and never repeats the signal values. No guest name, device id, or staff identity is selected or returned.

### Media storage

Uploaded files are stored on the server disk under `Media:RootPath` with opaque keys of the form `platform/<id>` or `tenants/<tenantId>/<id>`; the client file name is never used on disk and never trusted. Every upload is validated before it is stored: the closed purpose list is payment proof, refund evidence, menu import, and branding image; only JPEG, PNG, and WebP are accepted for payment proofs and branding images, and PDF is added for refund evidence and menu imports. The validator reads the leading bytes and accepts only a JPEG, PNG, WebP, or PDF signature that the purpose allows, so a renamed or mislabelled file is rejected; empty and oversize content is rejected with the uniform `Media.InvalidFile` and `Media.TooLarge` errors, and a rejected upload stores nothing. Files are not served as static files and no endpoint returns them yet; later tasks serve them only through authorized endpoints. The root path must be outside the repository and outside any web-served folder, must be included in backups (backup retention and restore cadence remain open under PRD TBD-19), and the disk space is shared with the application. Startup fails when the setting is missing, relative, inside the content root, or inside a `wwwroot` folder, and when `Media:MaxBytes` is outside its allowed range.

## Task 47 branch assignment and catalog changes

`GET` and `PUT /t/{slug}/api/v1/branches/{branchId}/menu/products/{productId}/station-assignment`
require `menu.manage` and enforce branch scope. Readiness is required. PUT accepts an explicit
nullable `stationId` and the branch assignment `concurrencyToken`. A null station clears the
current assignment and retains its history. The token is scoped to the product and branch.
Routing states are Assigned, Unassigned, StationInactive and BranchInactive. Changes in product
availability leave the route state unchanged. The ordering policy combines product availability
with route eligibility. Pending routing migration returns 409 Products.RoutingNotReady.

Product catalog reads and writes return 409 Products.CatalogSchemaNotReady while the tenant has
the expansion schema. They require the finalized tag identity key. This check is independent of
routing readiness and leaves unrelated tenant APIs available.

Ordinary product reads enforce effective category visibility. A caller with `menu.manage` may
request `includeHiddenCategories=true` on catalog list and detail. Product requests use
`tags` objects with a `tag` label and optional `id`. Updates identify existing active tags by ID.
Omitted active tags are logically deactivated. Restoration of inactive tag IDs remains open.
Product lifecycle actions also accept `includeHiddenCategories=true` with `menu.manage`.
Without authorized opt-in, hidden and missing products both return `404 Products.NotFound`,
including when the token supplied for a hidden product is stale. The lifecycle command checks
visibility before acquiring a product row lock or making a change. Both product creation and
listing also return `404 Tenant.Unavailable` when Tenant resolution fails.
General catalog writes reject the legacy `stationId` field. Product image support remains deferred
under FR-MENU-002.
